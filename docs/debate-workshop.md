# Debate Workshop Feature

The debate workshop is a separate, buildless page at `debate.html`. The admin feature selector is `admin.html`; the member lobby is `index.html`. It shares the club member roster but stores workshop state under `/debate_sessions`, separate from book voting data. The current unfinished session ID is published at `/active_debate_session` as soon as the session is created. The lobby advertises it only after the host starts Round 1.

## Entry modes

- Host: `debate.html?mode=host&admin=1` (requires the authorized Google account)
- Projection: generated by the host for the active session
- Participant: scan the session QR code or open the generated join link

The admin route requires the configured Google account UID in the client. Realtime Database Security Rules must also restrict admin writes to that UID; a browser check alone is not a security boundary.

## Module ownership

- `assets/js/debate/config.js` — Firebase configuration and initialization.
- `assets/js/debate/session-service.js` — Realtime Database subscriptions and writes.
- `assets/js/debate/i18n.js` — EN/DE text and workshop rules.
- `assets/js/debate/views.js` — role-specific markup and state rendering.
- `assets/js/debate/app.js` — route selection, application state, and event coordination.
- `assets/css/debate.css` — page-level styles shared by the three modes.

The page uses native ES modules and relative URLs. It requires no package manager, bundler, or build step.

## Session flow

The host creates a workshop from Control with one statement per round, three reflection questions, and host and secretary selected from the shared voting roster. Notes are entered later in the internal card in Settings; they are saved with the session and history but never rendered on member screens. Settings also contains a speaking timer selector with 3, 5, 10, 15, 20, 25, and 30 minutes per person. The default is 3 minutes. A changed duration applies to subsequent speaking turns; an active or paused turn retains its remaining time. Existing sessions with a different duration between 3 and 30 minutes continue to run at their saved duration until the host chooses a listed option. The chosen duration is stored under `settings/turnDurationMs` and included in history.

Members choose their roster name in the lobby; that identity carries into the event, and the debate page joins the selected member automatically. Round 1 choices can be changed; Round 2 choices are written once. The Control tab shows Round 1 above Round 2, each with right-aligned Start and End buttons plus per-speaker start, pause, resume, and finish controls. Ending Round 1 unlocks and brightens Round 2; ending Round 2 unlocks reflection. Ending a round with unfinished turns requires confirmation. Ended or not-yet-active rounds remain dimmed. Control, Settings, and History use the same pill tab treatment as Voting. The admin sees a centered, simplified live projection preview, plus joined and currently online member counts. The projection shows aggregate side counts, the current statement, speaker, timer, and the session's reflection questions. Members can join during reflection and see those questions on their own screens. Admin, projection, and member views show the workshop ID, creation time, participant count, and open or closed status. Expired projection and member links show the last workshop and a link expiry notice; the projector marks its QR code as expired. Round 2 rule 3 remains unspecified until the club supplies it.
Start Round is disabled and dimmed immediately when pressed, remains disabled while the database write is pending, and stays disabled after that round begins. A failed write restores the button when the round is still eligible to start.
Starting Round 1 stores `startedAt`. After a workshop ends, admin, projection, and member pages show a Last workshop label beside the closed status pill, the short ID, start time, end time, and participant count. Older sessions without `startedAt` show their creation time with a Created label instead of claiming it is the start time.
On expired projection and member links, the link-expiry notice appears directly below the ended-workshop title; the former Round 1 statement summary is not shown.
The UI shows only the last five characters of the workshop ID; links, database keys, and session operations use the full ID. Once joined, the member view shows the selected name and does not offer a name change. Leaving the workshop removes that member's participant record, presence, both round choices, and completed turns from the active session. The current tab then asks the member to reopen the workshop in a new tab to choose a name again. The projection places reflection questions in the upper content area and centers the QR code in its card. History presents each finished workshop as aligned report and participant-result tables.
The participant result table uses two-character codes in Round 1, Round 2 order: choices use `1` for TRUE, `0` for FALSE, and `–` for no choice; speaking uses `F` for a completed turn and `x` when no completed turn was recorded. The current session data records completed turns but not a durable start event, so `x` can also include a started turn that was not finished before the round ended.

Member presence is stored per browser tab under each session's `presence` node. Each tab registers a Realtime Database disconnect cleanup, and page exit attempts immediate cleanup. The admin count includes distinct members with at least one connected tab; `participants` retains members who close the page, but explicit Leave removes their participant record and results. The online count reflects the database connection state and may lag briefly when a network connection disappears unexpectedly. The live database rules must permit the member's multi-path removal under `participants`, `presence`, `choices`, and `turns`; the rules are not stored in this repository. Name selection alone is not an identity check, so the live rules should also enforce the member proof used by the lobby before allowing these writes.
Settings includes a per-name join limit (default 3, configurable from 1 to 10). A transaction on `joinAccess/{memberId}` counts each new tab admission. The admission ID is stored in that tab's session storage, so refreshing the same tab does not consume another entry. Explicit Leave removes that tab's admission ID from storage but preserves the counter in the workshop. Once the count reaches the limit, the Settings warning lists the name and count; new admissions are rejected until the admin uses Unblock to reset the count. With a fixed roster and no admin resets, normal client admissions are bounded by the limit times the number of names. This bound does not cover blocked requests or clients that bypass the app. The client-side check is a workflow guard, not a security boundary: the live Firebase rules must prevent direct writes that bypass `joinAccess` before this can be relied on against deliberate abuse.

The internal card is hidden from member and projection views, but the current Realtime Database session record still contains its fields. The deployed database rules must be reviewed before treating notes as confidential; strict confidentiality requires an admin-only data path and a session-data migration.

The host route first checks `/active_debate_session` and reopens its unfinished session, even when entered again from `admin.html` without a session ID. Starting another session is only possible after the current one ends. Ending writes `endedAt`, changes the session status to `ended`, and clears the current-session pointer. Completed records remain under `/debate_sessions` and appear in the host dashboard's history with statements, roles, participants, choices, completed turns, reflection questions, and notes. Realtime Database rules must allow the authorized admin to read the session collection for history and to update the current-session pointer.
